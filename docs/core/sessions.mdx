title: Sessions

Each ACP session owns one supervised `hermes serve` runtime and one isolated
`HERMES_HOME` generation materialized under the scratch parent (`WithScratchDir`, or the
system temp directory by default). The adapter talks to the native dashboard
gateway over loopback WebSocket JSON-RPC. Sessions are independent: one crashing
or ending never touches another's home or process.

## Lifecycle

The adapter implements the full ACP session lifecycle plus a native fork
extension:

- `session/new`
- `session/load`
- `session/resume`
- `session/list`
- `session/close`
- `session/delete`
- `_hermes/session/fork`

## Identity mapping

ACP session IDs are adapter-owned and stable across restarts. The native durable
Hermes session key is recorded in the `idmap` store subpath so a stored session
can be rehydrated later, while live gateway session IDs are runtime-only and are
never persisted.

## Load, resume, and delete

`session/load` hydrates native state, resumes the stored Hermes session, and
replays `session.history` to the ACP client so the host rebuilds the
conversation. `session/resume` hydrates and resumes the same way but skips the
replay, for hosts that only need to continue the turn stream.

`session/delete` tombstones the ACP store first, then best-effort deletes native
state; a native missing-session response counts as success, so delete is
idempotent.

Durable rehydration depends on a configured store — see
[Session store](/docs/features/session-store).

On `session/close`, an idle session is snapshotted synchronously before Hermes
shutdown removes its isolated XDG root. Sessions with a turn, permission,
elicitation, or generation still pending are closed without a fresh snapshot.

Cancellation and timeout are destructive runtime boundaries. The adapter first
interrupts Hermes, then completes the selected platform containment boundary
before the prompt settles. Every new, loaded, resumed, forked, or lazily rebuilt
runtime uses a fresh physical generation root; durable continuity comes only
from the committed snapshot. The logical ACP session remains active; its next prompt recreates the home from the last committed snapshot and resumes
the same native durable session key. A stale cancel nonce cannot target that
replacement runtime.
