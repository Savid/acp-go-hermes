---
title: Authentication
description: Agent auth stays native, while provider OAuth is coordinated through six values-free extension methods.
---

Hermes owns authentication and every provider credential byte. The adapter
coordinates native OAuth flows and records only values-free lineage.

## Standalone credential input

The standalone root supervisor never forwards its ambient environment.
To pass provider API-key variables, name each variable explicitly in the
`inheritEnvironment` array of the root-owned
`-process-isolation-config` policy. The value must be set in the supervisor
environment or startup fails; identity, path, loader, XDG/native-home, and
adapter-private variables cannot be inherited. File-backed or provider-broker
credentials must live only in the explicit target-owned native home described
by the adapter. No standalone path reads root `HOME`, root native config, or
an unlisted root credential.

## No ACP auth methods

The agent advertises `authMethods: []`, rejects `authenticate`, and treats
`logout` as a no-op. ACP clients do not authenticate the Hermes harness.

## Native state boundaries

Every ACP session has an isolated, ephemeral `HERMES_HOME`. Session config,
SQLite state, and runtime files cannot leak between sessions.

Provider auth uses a separate, durable `HERMES_AUTH_HOME`. Every session process
receives the same canonical path, and native Hermes performs all credential
reads and writes there. The adapter never parses, copies, returns, injects, or
snapshots credential material.

The launch environment also sets a random
`HERMES_DASHBOARD_SESSION_TOKEN`, `PYTHONUNBUFFERED=1`, and a private browser
shim. The shim intercepts Hermes browser launches so the authorization URL can
be relayed to the caller instead of opening on the worker desktop. Windows
rejects every native Hermes launch at the mandatory Unix UID/GID identity
boundary, so authorization is unavailable there. Independently, its browser
launch cannot be contained.

## Configuration

Provider auth requires both:

- `WithProviderAuthHome` / `-hermes-provider-auth-home`: the absolute durable native
  credential residence supplied to Hermes as `HERMES_AUTH_HOME`.
- `WithProviderAuthRoot` / `-provider-auth-root`: the absolute durable root for
  the adapter's values-free ledger.

`WithProviderAuthDirectHome` / `-provider-auth-direct-home` is part of the
uniform adapter surface but unsupported by Hermes. A non-empty value fails
closed at session start.

The directories are created with mode `0700`; ledger entries use mode `0600`
and atomic, fsynced writes. The ledger is scoped by the canonical auth-home path,
so two native homes under one ledger root cannot observe or mutate each other's
lineage.

If either path is missing, relative, or cannot be prepared, provider auth is not
advertised.

## Capability

When enabled, `initialize` advertises exactly:

```json
{
  "providerAuth": {
    "methods": [
      "_hermes/auth/methods",
      "_hermes/auth/authorize",
      "_hermes/auth/callback",
      "_hermes/auth/status",
      "_hermes/auth/cancel",
      "_hermes/auth/inventory"
    ]
  }
}
```

## Catalog

`_hermes/auth/methods` reads Hermes' native provider catalog and publishes only
OAuth `device_code` and `pkce` flows. External credential discovery and API-key
entry are not provider-auth methods.

The provider label is the native name, NFC-normalized, limited to 256 bytes, and
restricted to display-safe Unicode categories. Native status objects are
decoded through a fixed allowlist; raw provider fields do not cross the Go
boundary.

Each response carries a fresh `generation` naming that exact catalog.
`authorize` must return it as `methodsGeneration`, so a stale selection cannot
silently target a changed provider.

## Flows

`authorize` starts at most one flow for a provider and supersedes an older flow
for that provider, including one started from another session:

- `device_code` returns `interaction: "wait"`, an HTTPS verification URL, a
  user code, and a polling hint.
- `pkce` returns `interaction: "callback"`, an HTTPS authorization URL, and
  `callbackInput: "code"`.

The effective deadline is the earlier of the native expiry and 15 minutes.
`status` polls no faster than the larger of the native interval and five
seconds. Native states are closed to `pending`, `approved`, `denied`, `expired`,
and `error`; unknown values fail closed.

An approved native flow means Hermes has already persisted its credential in
`HERMES_AUTH_HOME`. The adapter records the confirmed connection revision and
binding generation, then reports `authenticated`. It never reads the credential
to prove completion.

Repeating an `authorizeRequestId` replays the same presentation without another
native start. `cancel` terminalizes the flow and invokes native cancellation.
Closing a session cancels its pending flows; the durable auth home and ledger
remain available to later sessions and process restarts.

## Inventory

`_hermes/auth/inventory` combines two values-free facts:

1. a confirmed ledger lineage for the requested connection; and
2. Hermes' native `status.logged_in` boolean for that provider.

`proofSource` is `confirmed_present` when both agree and
`confirmed_absent` when confirmed lineage exists but Hermes reports logged out.
Ambient native logins without adapter lineage are not attributed to a
connection.

## Store exclusion

`HERMES_AUTH_HOME` is outside every session home and is never part of a
`SessionStore` snapshot. Credential-bearing native files and credential tables
are also excluded or scrubbed from session snapshots.

Every provider-auth error uses the closed `hermes_auth_failed` shape. Native
response bodies, token previews, authorization secrets, and child stderr never
appear in it.
