---
title: Permissions
description: How native Hermes approval requests become ACP permission prompts and how answers flow back.
---

When Hermes needs approval to act, the adapter surfaces it to the ACP host as a
permission prompt and relays the host's answer back to Hermes. The flow is
load-bearing for user trust and is never silently auto-approved.

## Request mapping

A native `approval.request` gateway event maps to an ACP
`session/request_permission` request. The adapter presents three options:

Hermes 0.20.0's session-keyed `approval.request` payload has no request or tool
identifier. The owning actor derives an adapter-owned permission-request
identity inside the exact cycle, and never treats a command string as a tool
identity. Where exactly one native tool is active, the adapter takes that exact
native `tool_id` and uses it only as the ACP `toolCallId`. Hermes emits
`tool.start` only for a progress-enabled surface and runs tool calls
concurrently, so an approval also reaches the adapter with no active native tool
or with several; those bind to the permission-request identity instead, and the
approval is presented either way. Terminal IDs and callbacks outside their exact
active turn are still rejected without invoking the ACP permission callback.

An approval that minted its own identity settles exactly as a tool-bound one
does. Native `approval.respond` carries the session and the chosen option and
nothing else — Hermes resolves the session's oldest waiting approval — so the
adapter checks that the answer belongs to the exact cycle that emitted the
request and never gates the answer on a native tool identity Hermes did not
give it.

The cycle actor keys held controls by both control kind and request ID and
rejects a duplicate before emitting it. A native clarification whose ID equals
an adapter-generated permission ID therefore cannot replace the permission's
owner.

Before invoking `session/request_permission`, the adapter publishes the
correlated ID as a pending tool call with the active turn's route envelope.

| Option id | ACP kind | Native reply |
|---|---|---|
| `once` | `allow_once` | `once` |
| `always` | `allow_always` | `always` |
| `reject` | `reject_once` | `reject` |

The host's selected option is relayed to Hermes through native
`approval.respond`.

## Cancellation

On cancellation, pending native permission requests are answered with `reject`
carrying a cancelled explanation, and the ACP prompt returns the `cancelled`
stop reason. If the client is unavailable when a request arrives, the adapter
also replies `reject` so Hermes never blocks on a missing host.

<Note>
Permission decisions are session-scoped. `always` grants persist only within the
session that made them; they are copied to a new session only through explicit
fork behavior.
</Note>
