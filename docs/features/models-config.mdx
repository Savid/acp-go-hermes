---
title: Models And Config
description: Select the session model and seed Hermes' own config to route through a gateway.
---

Pick the model for a session and, when you need it, hand Hermes its own config so
it routes prompts through a gateway of your choice — without touching the
caller's real Hermes home.

## Model selector

The model selector is an ACP config option with id `model` and category `model`.
Values are built from native gateway `model.options` results as `provider/model`.
Each advertised option carries per-model `_meta.hermes` metadata — see
[Metadata](/docs/reference/meta).

Those advertised values are a menu for the host, not an accepted set. A
`provider/model` value absent from the latest menu still travels to Hermes from
lifecycle metadata, `session/set_session_config_option`, and the next prompt.
Hermes decides whether it resolves: an accepted selection becomes the config
option's exact `currentValue`, while a native refusal returns invalid params
with `error: hermes_model_selection_refused` and `field: value`. Native error
text is not copied across the ACP boundary.
Session creation may accept a selection whose provider cannot be resolved until
the first prompt; that prompt then returns Hermes' native turn failure. A failed
`model.options` read can hide the menu, but it does not reject a model mutation
that Hermes already accepted.

Hermes draws its line at the provider. A selection naming a provider it does not
have is refused; a model no provider advertises is taken, which is why the
catalogue cannot be read as an acceptance set. Its acknowledgement of an accepted
selection echoes the key, value, and scope it applied, so the adapter needs no
read-back to confirm one — a mismatched echo is itself an error.

### Selection values are provider-qualified

A model value is refused locally, before any native call, only when it cannot
name a provider and a model at all: it must split on `/` into two tokens, neither
empty, neither beginning with `--`, and neither carrying whitespace. That is a
question about the value's shape and never about which models exist. Every door
that must carry a value into a session's provider and model — the config option
and an active `session/load` or `session/resume` — refuses the same shapes, so
none of them silently degrades a value another would reject.

Session creation is the exception, and only because nothing is degraded there:
`session/new` hands the value to Hermes, which carries model and provider as
separate fields and resolves an unqualified model against its own catalogue.

An advertised option's `_meta.hermes` metadata carries the selection value and
nothing else: the gateway catalogue's per-model `fast`/`reasoning` capability map
is not republished, and it names no input/output modality or generator fields at
all. The current driven gateway does not expose an exhaustive selected-model
image modality source, so image prompt validation uses `unknown` model support
and forwards valid images to Hermes.

## Effort selector

The effort selector is an ACP config option with id `effort` and category
`thought_level`. Its values are Hermes's own reasoning levels, `none`,
`minimal`, `low`, `medium`, `high`, `xhigh`, `max`, and `ultra`, where `none`
disables thinking. Hermes clamps a level to what the model's provider accepts.

The current value is the level the session runs at. A session that selected
none reports the level Hermes resolved for it, which is `agent.reasoning_effort`
or a matching `agent.reasoning_overrides` entry from the seeded `config.yaml`,
read back through the gateway. A selection, from `_meta.hermes.options.effort`
at creation, restore, or fork, or from `session/set_session_config_option`,
reaches Hermes as a session-scoped `config.set reasoning` and never rewrites the
global config. The level Hermes acknowledges becomes the option's exact
`currentValue`, and a restored session rebinds the level its snapshot recorded.

A value outside the vocabulary is refused locally as an unsupported `value`:
Hermes's reasoning key also takes display words, and this option forwards only
levels. A native refusal returns invalid params with
`error: hermes_effort_selection_refused` and `field: value`.

No mode selector is advertised: Hermes exposes no approved programmatic
per-session agent/mode enumeration surface for this adapter. Structured output is
also not advertised; supplying `_meta.hermes.options.outputSchema` returns the
uniform unsupported-field error.

### Host-listed models

A host that knows what its endpoint serves lists those ids with
`WithConfiguredModels`, each as `<provider>/<model>`. Each id follows the
native rows on every route under the group its provider prefix names, created
when native enumeration has none, as the id alone with no metadata. An id
Hermes already enumerated keeps its native row. An empty, whitespace,
unqualified, or duplicate id fails construction.

## Seeding native config

Use `WithSeedFiles` (or the `-seed-file` CLI flag) to write Hermes' own config
into each session's isolated config root before Hermes launches. This is how you
point Hermes at a gateway such as LiteLLM. Every session is seeded fresh and
paths are confined to the config root.

Most seeded files are written verbatim. `config.yaml` is the exception: the
adapter also authors it to carry the `mcp_servers` block for session MCP servers,
so a seeded `config.yaml` is deep-merged with the adapter's managed `mcp_servers`
on top. The adapter wins for `mcp_servers`; your seed supplies the `model` block
and everything else. A session can therefore use a seeded `model` gateway and
wrapper-provided MCP servers at once.

<Warning>
Keep the API key in the environment (`WithEnv`) and reference it from the seeded
file by env-var indirection with Hermes' `key_env`. Never write the secret into
the seeded file — seeded files may be captured in snapshots.
</Warning>

```go
agent := hermesacp.NewAgent(
	hermesacp.WithEnv(map[string]string{
		"LITELLM_API_KEY": os.Getenv("LITELLM_API_KEY"),
	}),
	hermesacp.WithSeedFiles(map[string]string{
		"config.yaml": `model:
  provider: custom
  base_url: http://localhost:4000/v1
  key_env: LITELLM_API_KEY
  default: gpt-4o
`,
	}),
)
```

The seeded `config.yaml` lands at `config.yaml` under the session's resolved
native config root, so Hermes reads it as its own configuration and routes the
`default` model through the LiteLLM gateway at `base_url`, authenticating with
the key named by `key_env`.
