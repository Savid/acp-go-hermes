---
title: Session Store
description: Wire a durable store to persist sessions and how the hermes-state-db-v1 snapshot is shaped.
---

Persist sessions across adapter restarts by wiring a `SessionStore`. Without one,
the adapter keeps sessions in memory only; with one, completed turns are
snapshotted so a session can be reloaded or resumed later.

## Wiring a store

Pass a store with `WithSessionStore`. The adapter ships an in-memory
implementation for tests and single-process use, and the `SessionStore`
interface lets a host supply durable backing:

```go
store := hermesacp.NewInMemorySessionStore()

agent := hermesacp.NewAgent(
	hermesacp.WithSessionStore(store),
	hermesacp.WithSessionStoreLoadTimeout(10*time.Second),
)
```

`WithSessionStoreLoadTimeout` bounds each store read; it defaults to 10
seconds. Store writes (snapshot `Replace` commits and `session/delete`
tombstones) run under a separate fixed 60-second bound, so a slow but
successful commit never fails a prompt just because it outlived the read
budget. The `SessionStore` interface (`Append`, `Load`, `Replace`, `Delete`,
`ListSessions`, `ListSubkeys`) is indexed in the [Go API](/docs/reference/go-api).

## Snapshot shape

`SessionStoreFormat` is `hermes-state-db-v1`. The store writes a complete
snapshot after each completed turn:

- the main snapshot entry
- `idmap`
- `state-db`

The `state-db` archive contains `state.db`, `state.db-wal`, and `state.db-shm`
when present. Its compressed tar bytes are split into ordered 256 KiB chunks;
each `tar+zstd+base64` entry carries a zero-based sequence, a final marker, and
the full-archive SHA-256. Restore requires a contiguous sequence, exactly one
terminal chunk, matching size/checksum metadata, and then reassembles the
archive into a fresh per-session `HERMES_HOME`.

The `idmap` subpath records the ACP session ID, durable Hermes session key, and
fork lineage. Live gateway session IDs and auth tokens are not persisted.

## Restore

Restore after native deletion hydrates `state-db` into a fresh home, calls native
`session.resume`, and — for `session/load` — replays `session.history` to the ACP
client.

`session/close` captures its final eligible snapshot before stopping the native
client, because managed client shutdown removes the isolated XDG root. Close
still skips snapshotting while a turn, permission, elicitation, or generation
is pending, and it always proceeds with native teardown even if the snapshot
fails.

<Note>
Snapshots exclude credential-bearing files and scrub credential tables from the
SQLite archive, so a store never captures provider secrets.
</Note>
