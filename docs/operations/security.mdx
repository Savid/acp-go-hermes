---
title: Security
description: Process, filesystem, credential, browser, and protocol boundaries.
---

The adapter has two native execution modes. The standalone command runs Hermes
as the adapter's own operating-system account. An embedded host can supply
`WithHostAuthority` for host-managed process and filesystem containment.

## Standalone command boundary

The command captures its environment once, removes adapter-private and
native-state variables, and starts each Hermes process directly as the current
account. Executable lookup follows the captured `PATH`.

This mode makes no cross-account containment claim. Operators who need stronger
separation should run the command inside their own service, container, or
sandbox boundary, or embed the package with a host authority.

## Loopback gateway

Each session starts `hermes serve` on a freshly selected loopback port with a
random dashboard token. The token is passed through the native environment and
on the private WebSocket request. It is never published through ACP metadata or
logs.

## Browser launch containment

The adapter materializes a private browser-launcher shim before native startup
and places it ahead of the native `PATH`. Provider authorization refuses before
the native auth call when the session has no shim. The Linux native-browser
canary verifies the production adapter reaches the authorization URL without
executing an unshimmed desktop launcher.

## Native process containment

`WithHostAuthority` supplies a borrowed `HostAuthority` already bound by the
embedding host. The authority provides a complete native environment, prepares
fully materialized trees, starts native work with host-created stdio, reclaims
trees after process terminality, and owns whole-tree revocation.

The adapter routes the version probe and every session `hermes serve` launch
through `StartNative`. It passes the configured executable as a logical
selector; it does not resolve or inspect that selector in managed mode. A nil,
typed-nil, panicking, or otherwise unusable authority fails before native
filesystem mutation or launch. Authority errors never retry through direct
execution.

For each native tree the adapter follows one order:

1. materialize all configuration, seeds, and browser-shim files;
2. call `PrepareNativeTree`;
3. perform no filesystem operation at or below that tree while prepared;
4. close the WebSocket normally, call `Revoke`, and join `Wait`; and
5. call `ReclaimNativeTree` before removing adapter scratch.

`Wait` is the terminal process proof. Gateway EOF alone does not establish
terminality. `ErrHostAuthorityUnavailable` stops managed admission,
`ErrContainmentIncomplete` retains native trees for host cleanup, and
`ErrNativeTreeBusy` means reclaim was refused before changing tree ownership.

The session control lock lives in runtime scratch outside the prepared native
home. Its descriptor remains in the adapter and is not inherited by Hermes.

Provider-auth extensions are unavailable when a host authority is supplied.
The agent still initializes and serves ordinary ACP session methods.

## Local read surface

`WithInputHandoffRoot` enables digest-verified local image handoff beneath one
absolute read-only root. The adapter resolves and reads files there but never
writes, moves, or removes them. Native Hermes receives image bytes, not the
source pathname.

Seed files are copied into a session tree before it is prepared. Their relative
paths cannot be absolute, empty, or escape with `..`.

## Stdout discipline

Stdout is reserved for ACP JSON-RPC. Structured diagnostics and native process
output go to stderr or the configured logger. Error mapping omits native
transport bodies and credential values.

## Credentials never leave the process

Hermes owns provider credential bytes. In ordinary shared-home mode the adapter
stores only a values-free provider-auth ledger and does not parse, copy, return,
inject, or snapshot Hermes credential files. Managed authority mode does not
advertise the provider-auth extension methods.
