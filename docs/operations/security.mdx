title: Security
description: The trust boundaries an operator relies on — loopback gating, stdout discipline, and credential exclusion.

The adapter is built so that running it does not widen your attack surface: the
gateway stays on loopback, the protocol stream stays clean, and stored snapshots
never carry secrets.

## Standalone command boundary

The standalone command launches native work only on Linux and requires the
root-owned mode-`0600` `-process-isolation-config` policy. Resolution walks
from an open `/` descriptor with `openat` and `O_NOFOLLOW`; every ancestor
must be root-owned and not writable by group or other, and the final single-link
policy inode is read through the descriptor that was validated. The configured
account home is resolved the same way, must be a target-owned mode-`0700`
directory beneath protected root-owned ancestry, and cannot be `/root` or
`/nonexistent`.

The adapter remains root, but its ambient environment is never copied wholesale
to the child. Only the complete literal `baseEnvironment` plus names in
`inheritEnvironment` reach native work. The CLI refuses Darwin, Windows, and
other platforms; Darwin best-effort containment remains an explicit
embedded-Go option only. `-version` and Darwin containment diagnostics launch
no native worker and are exempt.

## Loopback gateway

Each `hermes serve` process binds to `127.0.0.1` and gates the dashboard
WebSocket with a per-session random `HERMES_DASHBOARD_SESSION_TOKEN`. Nothing
listens off-host.

## Native process containment

Hermes' cooperative interrupt stops its foreground command but intentionally
leaves background servers and watchers running. The adapter therefore closes
the selected native containment boundary before cancellation settles. On Linux,
a dedicated self-executed subreaper owns Hermes and every orphaned tool
descendant, including processes that detach with `setsid(2)`; pidfd-bound
signals, an authoritative kernel `ECHILD` fence after the direct root waiter
settles, and an explicit proof pipe make fork/reparent races and supervisor
death fail closed. Windows rejects native launch before spawning Hermes because
its process API cannot apply the mandatory Unix UID/GID identity boundary with
empty supplementary groups. A Windows cross-compile proves only that this
refusal path builds; it does not establish runtime support.

The Linux supervisor stays root and runs from `/` with a closed private
environment. Sealed launch configuration carries the target identity and native
environment; only `hermes serve` receives the configured UID/GID with no
supplementary groups. Before native start the supervisor acquires the
root-owned `/run/acp-go/agent-identities/<uid>.lock` and holds it until the
descendant wait queue is empty. Hermes inherits none of the launch, control,
proof, or lock descriptors, so it cannot signal its supervisor, forge
completion, or overlap another native tree using the same host identity.

Native session startup fails with `ErrProcessContainmentIncomplete` where the
adapter cannot establish its selected boundary. Embedded Darwin hosts default
to rejecting startup. `WithDarwinBestEffortContainment` explicitly accepts a
weaker boundary:
the adapter controls only the original process group. A descendant that calls
`setsid(2)` can escape and survive; numeric PGID reuse can make later group
signals collateral; environment-marker correlation is neither ownership nor
proof of absence and can be scrubbed.

Every opted-in Darwin launch gets a fresh mode-0700 generation root and an
atomic mode-0600 record under `acp-go-hermes-containment` in the scratch parent.
The contained `hermes --version` discovery launch has its own discovery native-
root admission and scratch reservation, separate from the session server's
admissions and generation.
Incomplete cleanup quarantines that root and its host admission ownership.
Operators can inspect records with `acp-go-hermes containment diagnose` and may
run the explicitly forced cleanup command after reviewing correlated and
ambiguous PIDs. Cleanup revalidates UID, process start identity, and both exact
markers before every individual PID signal; it never treats a recorded PID or
PGID as signal authority. PID-by-PID cleanup has a PID-reuse time-of-check/time-of-use race and can signal an unrelated reused PID; correlation is not ownership or proof of absence; inherited markers can be scrubbed.

## Local read surface

The adapter reads exactly one host-supplied location on disk, and only when the
host opts in with `WithInputHandoffRoot`. Every other inbound payload arrives in
the ACP frame; no prompt URI is ever fetched, local or remote.

A block whose declared media type or declared size fails its gate is refused
before the root is opened at all, so a refusal on the declaration reveals nothing
about whether the file it named exists.

Inside that root the adapter is read-only and bounded. Containment is enforced
by the kernel: the root is opened once per prompt and every file is opened
relative to that descriptor, so a name leading out of the root is refused as
part of the open rather than followed, and the opened descriptor must be a
regular file, because a root bounds where a name may lead and not what kind of
object it names. Reads stop one byte past the size the block declared, and bytes
must match that size and hash to the digest the block declared or the turn is
rejected — a file whose contents changed underneath the host is never forwarded.
The adapter never writes, moves, or removes anything under the root, and the
path never appears in the native request, so nothing about the host's layout
reaches Hermes.

<Warning>
The handoff root is a read grant. Point it at a directory that holds only files
intended for this adapter — not at a session workspace or a shared parent of
other tenants' trees.
</Warning>

## Stdout discipline

Stdout is reserved exclusively for ACP JSON-RPC frames. Child process stdout and
stderr are never connected to the ACP stdout stream, so a chatty harness cannot
corrupt the protocol.

<Warning>
Never print to stdout from an embedding host — it is the ACP JSON-RPC channel.
Send all diagnostics to stderr or a logger.
</Warning>

## Credentials never leave the process

Session snapshots store only the Hermes state-database archive plus adapter
metadata. They exclude obvious credential-bearing files such as `auth.json`,
credential-named files, logs, caches, checkpoints, and backups; credential tables
in SQLite archives are scrubbed. Provider keys stay in the environment and are
never written into seeded files or the store.
